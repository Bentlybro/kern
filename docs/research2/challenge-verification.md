## Strongest objections
### [serious] The middle-path verdict's headline justification — "you keep the entire VS Code extension ecosystem — which raw LSP would cost you" — is the weakest link in the strongest recommendation. code-server cannot legally use Microsoft's Visual Studio Marketplace; it defaults to Open VSX. Open VSX is missing precisely the extensions that would motivate keeping the extension host at all: Pylance, the Microsoft C/C++ extension, the Remote-* pack, and (historically) the MS Python debugger build. So the extension host buys you Open VSX's subset, not "the ecosystem." The verdict is still right, but for a different reason: the value is the stable self-designed RPC boundary and the already-working extension host, not marketplace breadth.
  Mitigation: Rewrite the justification. Sell the middle path on protocol ownership (you design the wire format, it cannot break under you) and on zero incremental backend work, not on ecosystem retention. Then audit Open VSX for the five extensions you would actually use on a phone before assigning any weight to the ecosystem argument. Verified separately: the LSP servers you actually need (rust-analyzer, gopls) ship as Termux packages independent of any marketplace, which is the real reason this is low-risk.

### [manageable] The claim "A Kotlin client must send the exact commit hash... This is not a versioned protocol; it is a pinned one" is factually wrong as stated, and it is load-bearing for the difficulty argument. The actual guard in remoteExtensionHostAgentServer.ts is `if (rendererCommit && myCommit) { if (rendererCommit !== myCommit) return rejectWebSocketConnection('Client refused: version mismatch'); }`. `commit` is optional in the interface (`commit?: string`). A client that simply omits the field short-circuits the check entirely. The well-known community workaround of stripping `commit` from the server's product.json confirms the guard is conditional, not absolute.
  Mitigation: Correct the fact but keep the conclusion. The pin is weaker than claimed, which makes the handshake marginally easier — but the handshake was never the hard part. The 4,000-line RPC surface above it is, and nothing about the commit guard changes that. If anything this slightly strengthens the middle path, because it shows the barrier is complexity and churn rather than access control.

### [manageable] "has killed the one team that tried" is presented as evidence but I could not verify it from any primary source, and no such project surfaced in any of my fetches. Rhetorical claims dressed as findings are the most dangerous kind in a decision memo, because they are the parts a reader will not re-check. Similarly, the "4,000-line undocumented RPC surface" figure is unverified — the layered RPC design is real and I confirmed the framing layer, but the specific magnitude is an assertion.
  Mitigation: Strike the dead-team anecdote or name the project with a URL. Replace the line-count with what is actually verifiable and equally damning: two independent hand-rolled serialization layers (13-byte binary framing plus a bespoke VSBuffer type-tagged serializer with VQL lengths), zero schema, zero documentation, and a monthly release cadence upstream. That argument stands on facts I confirmed.

### [serious] sora-editor's bus-factor-of-1 risk is understated, and I found fresh evidence for it. The main branch's gradle/libs.versions.toml now pins AGP 9.2.1 and Kotlin 2.3.10 — an extremely aggressive toolchain. A single maintainer tracking bleeding-edge AGP means the version you depend on can become hard to build against your own app's toolchain, and the Code on the Go precedent (which pins the frozen 0.23.6 under the OLD io.github.Rosemoe group rather than tracking main) suggests serious downstream users deliberately do not follow this repo's head.
  Mitigation: Pin a specific released version (0.24.6) and vendor the source into your tree from day one rather than consuming it as a remote dependency. You already need to patch into its package namespace for package-private APIs — the claim itself verifies Code on the Go had to do exactly this with ContentLockAccessor and IDEEditorSearcher — so vendoring is not extra work, it is work you were going to do anyway. Vendoring also makes the LGPL relinking obligation trivially satisfied.

### [serious] The Android platform constraints named in extension-loss as "the things that can genuinely kill this project" — W^X/SELinux blocking execve from app-private storage at targetSdk >= 29, /sdcard noexec, background language-server kills, and rust-analyzer's 1–3 GB working set — are the highest-consequence claims in the entire set and I verified NONE of them this session. They are also the only claims that could invalidate the whole architecture rather than just redirect it. rust-analyzer's memory footprint in particular is the one number that decides whether Rust support is real on a phone.
  Mitigation: These are all empirically testable on the device in under a day, and they gate everything else. Before writing any Kotlin: measure rust-analyzer RSS on an actual Fold8 workspace, and confirm the foreground-service requirement by backgrounding the app with a server attached. Note the mitigating fact I did verify: rust-analyzer is a maintained first-class Termux aarch64 package (rebuilt 2026-08-03, no blacklisted arches), so the execve question is already answered in practice for the Termux-hosted path — Termux solved it. It is only an open question if you bundle your own userland.

### [manageable] The claim that LSP4J's editor-lsp is a safe, copyable precedent needs a version caveat the verdict does not give. sora-editor's main branch now pins lsp4j = 1.0.0, and LSP4J 1.0.0 is a breaking release: it removed the org.eclipse.lsp4j.websocket module outright, changed TextDocumentEdit.edits, Diagnostic.message and DocumentFilter.pattern types, and dropped throws IOException from several methods. Meanwhile Code on the Go — the only shipping Android IDE using LSP4J — is still on 0.22.0. So the "proven on Android" evidence and the "current version" are not the same artifact.
  Mitigation: Correct the record: LSP4J's Java baseline is 11, not 21 (versions.gradle says `'java': '11'`; a Java 21 figure circulating in search results refers to the Eclipse IDE requirement, not LSP4J bytecode), so 1.0.0 is safe for Android from a bytecode standpoint. Choose 1.0.0 deliberately for LSP 3.18 / DAP 1.70 support and budget for the breaking changes, or pin 0.24.x to match the better-tested Android path. Either is defensible; drifting into it accidentally is not.

### [manageable] The native-editor verdict softens code folding into "next-ish but unshipped," which reads as speculation. It is more concrete than that, and slightly better news than the verdict conveys — but the multi-cursor picture is worse. Issue #85 (Support code folding) is assigned to milestone 0.25.0 and has 6 comments, not the zero-signal state implied. Issue #798 (multiple cursor editing) has 0 comments and no milestone since 2026-01-28 — that is not a roadmap item, that is an unacknowledged request.
  Mitigation: Report the asymmetry honestly: folding has a milestone and may arrive for free; multi-cursor has nothing and should be treated as permanently absent unless you build it. On a 7-inch foldable, multi-cursor is a low-value feature anyway — this is the right thing to concede rather than plan around.

### [manageable] The signing-bypass finding is correct but its durability is stated too confidently. `validate()` returns true only when `!message.id`, and the message id is set by the SERVER — so the bypass depends on the server ALSO lacking vsda. That is true of code-server today, but it is a property of the deployment, not of the protocol, and it is exactly the kind of thing that changes without notice. Additionally, code-server layers its own connection-token auth on top, which is a real barrier the analysis does not mention.
  Mitigation: Only matters if the remote-protocol path is chosen, which it should not be. But if any part of it is used, treat the bypass as an observed property of a specific code-server build to be re-verified per upgrade, and account for the connection token separately.

## RECOMMENDATION
Adopt the verdicts, with the middle path as primary — but fix its justification and re-sequence the work.

1. Take the middle path (custom VS Code extension exposing a self-designed JSON-RPC over WebSocket), and do it for the right reason. I verified all 24 `vscode.execute*Provider` commands are publicly documented with no stability caveat and no proposed-API gate. That is the real asset: a documented, stable surface you can build a private protocol on top of, using a backend that already works today. Do NOT justify it as "keeping the extension ecosystem" — code-server means Open VSX, not the Microsoft marketplace, and the extensions that would justify an extension host (Pylance, MS C/C++, Remote-*) are exactly the ones missing there. The honest pitch is: zero backend work, and a wire format that cannot break under you.

2. Reject the remote-protocol path, but on the correct grounds. My attempt to refute it partly succeeded — the commit pin is bypassable by omitting the field, and the signing bypass is verified real — so the path is EASIER than the verdict claims. It is still wrong, because the difficulty was never the handshake. It is two hand-rolled serialization layers with no schema and no docs, sitting under a monthly release cadence, for capabilities you already have. Drop the unverifiable "killed a team" anecdote; it weakens an argument that stands fine on verified facts. Separately, the VS Code Server license text I confirmed verbatim ("provide the software as a stand-alone offering or combine it with any of your applications for others to use") means code-server is the only legally safe target regardless.

3. Sequence deliberately: fold-native chrome FIRST, editor swap SECOND. This is the strongest and most underweighted advice in the whole set. The panes, insets, key row, and terminal view are pure client-side work, are the entire reason for this project, carry no protocol risk, and can ship while the WebView keeps serving the editing surface. Every architectural question in this document is deferrable behind that shell. Do not let the backend decision block the thing you actually want.

4. Before writing any Kotlin, spend one day on the device measuring the four things nobody verified. rust-analyzer RSS on a real Fold8 workspace, whether backgrounded servers survive without a foreground service, and the execve/W^X behavior for your chosen hosting model. These are the only claims in the set that could invalidate the architecture rather than redirect it, and they are the cheapest to test. Mitigating evidence I did verify: rust-analyzer is a first-class, actively rebuilt Termux aarch64 package, so Termux has already solved execve for you — that question is only open if you bundle your own userland.

5. Vendor sora-editor 0.24.6 rather than depending on it. Its main branch is on AGP 9.2.1 / Kotlin 2.3.10 with a single maintainer, and the one shipping Android IDE that uses it (Code on the Go) deliberately pins the frozen 0.23.6 instead of tracking head. You already need package-namespace patches for package-private APIs, so vendoring costs nothing extra and also makes the LGPL-2.1-or-later relinking obligation trivial. The license is genuinely clean against GPLv3 — I confirmed "or (at your option) any later version" in the actual CodeEditor.java header, and confirmed CodeEditor extends View, so the Compose-interop and ime-insets arguments hold.

6. Treat LSP4J as settled and cheap. The Gson-only claim is the single strongest fact in the document and it is even tighter than stated. Pick the version deliberately: 1.0.0 (what sora's head now uses, LSP 3.18/DAP 1.70, but breaking — websocket module removed, several public types changed) or 0.24.x (matches the better-tested Android path). The Java baseline is 11, not 21; do not let the circulating Java-21 misinformation scare you off this.

Bottom line: the analysis is right, better-researched than most decision memos, and its one genuinely soft spot is the ecosystem argument for the option it recommends. Fix that justification, delete the two unverifiable rhetorical flourishes, go measure the four Android facts, and start on the fold-native chrome tomorrow.
