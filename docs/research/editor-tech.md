# editor-tech

## Summary
For a touch-first Android IDE in 2026, the editor core choice comes down to CodeMirror 6 in a WebView versus the native sora-editor; Monaco remains explicitly non-mobile. Monaco's touch-support request (#1504) has sat open in the Backlog since 2019, selection handles are still missing as of a March 2025 issue, and the one community touch-selection PR was closed unmerged — mobile only works acceptably with a hardware keyboard (e.g., VSCodroid ships full VS Code Server + workbench in a WebView with an extra-keys row, requiring Android 13+/4GB RAM). CodeMirror 6 was built for touch/IME, is what Replit chose for its mobile editor, and shows active Android/GBoard fixes as recently as @codemirror/view 6.43.8 (Aug 4, 2026), though a long tail of GBoard composition bugs (autocorrect appending, double-space-as-backspace, suggestion-strip newline breakage) persists and is worked around release by release. Sora-editor is a mature native Android editor view (TextMate + tree-sitter + experimental lsp4j-based LSP module), actively maintained with releases through 0.24.6 (June 10, 2026), and gives the best native touch/magnifier/IME control — but its LSP client is marked experimental and its flagship consumer, AndroidIDE, is discontinued (community forks like Code on the Go continue). JetBrains Fleet was killed Dec 22, 2025 (pivoted to the macOS-only agentic "Air"), and Compose-native editor libraries remain toys, so there is no credible "newer" fourth option.

## Key facts
- Monaco touch support request (microsoft/monaco-editor #1504) opened July 9, 2019 is still open in the 'Backlog' milestone; issue #4860 (March 25, 2025) confirms draggable selection handles still don't exist and selection can only be grown via editor.action.smartSelect.expand.
- Community PR microsoft/monaco-editor #4623 adding touch-based text selection (opened July 30, 2024) was closed unmerged in November 2024 with no substantive maintainer review — Monaco mobile support is community-hack territory.
- Replit publicly chose CodeMirror 6 as its mobile editor (blog post 'A New Code Editor for Mobile', Sept 20, 2021), citing that CM6 was 'specifically designed with mobile in mind', and used Lezer incremental parsing to drive a smart symbol keyboard.
- CodeMirror is actively maintained for Android: @codemirror/view 6.43.8 (Aug 4, 2026) fixed Android scroll-into-view; 6.43.2 fixed Chrome Android tap-to-focus scrolling and native select-all; 6.38.4 worked around Chrome Android not firing compositionend.
- CodeMirror 6 still has documented GBoard bugs: autocorrect appends instead of replacing (codemirror/dev #467), double-space read as backspace (#685), suggestion strip breaking newline insertion (#1145), placeholder+fullstop emitting object-replacement chars (#1028).
- CM6 LSP path is mature: FurqanSoftware/codemirror-languageserver (original) and the actively maintained @marimo-team/codemirror-languageserver fork (v1.16.12, published ~July 2026) provide completion, hover, diagnostics, go-to-def, rename over WebSocket.
- sora-editor (Rosemoe) is actively maintained in 2026: releases 0.24.0 (Nov 18, 2025) through 0.24.6 (June 10, 2026, last API-21 release) verified via GitHub API; all tagged prerelease; modules: editor, editor-lsp, language-textmate, language-treesitter, language-java.
- sora-editor's editor-lsp is built on lsp4j, recommends socket connection to out-of-process language servers, supports completion/diagnostics/hover/signature-help/code-actions/formatting, but is explicitly labeled 'Experimental, work in progress' (semantic tokens still TODO).
- sora-editor 0.24.x added native oniguruma for TextMate ('60% less' highlighting time), tree-sitter cancellation tokens for large files, minimap (experimental), sticky scroll, inlay hints, text magnifier, and IME cursor-anchor fixes under wordwrap.
- AndroidIDE (sora-editor's flagship consumer) is discontinued — androidide.com is archived and says 'AndroidIDE is closing'; community fork 'Code on the Go' (App Dev for All nonprofit) continues offline-first on-device Android development.
- JetBrains Fleet was discontinued: unavailable for download since Dec 22, 2025; the Fleet platform was repurposed into 'Air', an agentic tool currently macOS-only in preview — Fleet is not a usable mobile editor-component source.
- VSCodroid demonstrates the WebView-workbench approach: VS Code Server (vscode-reh) as native ARM64 Node process + VS Code Web in a WebView over localhost, with an extra-keys row (Ctrl/Alt/Tab/Esc/arrows) and clipboard bridge; requires Android 13+, ARM64, WebView 105+, ~4GB RAM; extensions from Open VSX; MIT (Code-OSS based).
- Android WebViews deliberately restrict raw key events: Google's guidance is to stop relying on legacy key events for text input; intercepting hardware shortcuts requires overriding onCreateInputConnection/dispatchKeyEvent (or dispatchKeyShortcutEvent) at the native view layer.
- Termux's extra-keys (two configurable rows above the soft keyboard with sticky Ctrl/Alt, arrows, symbols, defined in ~/.termux/termux.properties) is the established pattern any serious mobile IDE must replicate; Samsung Keyboard and GBoard both offer split/thumb layouts on Fold-class devices, and the keyboard consumes a large fraction of the unfolded inner screen unless set to floating.

## Cross-cutting Android text problems
- **IME composition vs code**: GBoard's composing region + autocorrect actively fight symbol-dense text (period→auto-space, double-space→".", composing underlines spanning identifiers). Web editors can only set `autocomplete/autocorrect/spellcheck/autocapitalize` attributes on the contenteditable and hope the keyboard honors them; a native view sets `EditorInfo.inputType` (`TYPE_TEXT_FLAG_NO_SUGGESTIONS` / null-InputConnection tricks) directly — the single biggest native-vs-WebView advantage.
- **Extra-keys row**: Termux's two-row sticky-modifier extra-keys (termux.properties) is the proven pattern; VSCodroid replicates it (Ctrl/Alt/Tab/Esc/arrows). Any option needs this; in a WebView it must be a native bar injecting synthetic events or calling editor APIs over a JS bridge.
- **Hardware keyboard in WebViews**: Chrome-based WebViews deliver most printable/modifier keydowns to the page (Monaco/CM6 keymaps work), but Google deliberately limits legacy key events; system-level chords, Tab focus traversal, and IME-consumed keys need native `dispatchKeyEvent`/`dispatchKeyShortcutEvent` handling before the WebView sees them. Native views own the full pipeline.
- **Monospace fonts**: WebView = @font-face (JetBrains Mono etc., ligatures via font-feature-settings); sora-editor accepts custom Typeface with ligature toggle. Non-issue either way.
- **Foldables/split keyboard**: Samsung Keyboard and GBoard split into thumb halves on Fold inner screens and can float; a docked keyboard eats roughly the lower half of the unfolded panel. The app must handle `WindowInsetsCompat.ime()` resize properly (WebView viewport resize is laggier than a native view's `adjustResize`), keep the cursor scrolled into view (exactly the class of bug CM 6.43.x fixed), and support the keyboard in floating mode.

## Recommendations
**(a) WebView/VS Code-workbench approach**: Do NOT bet on bare Monaco — its touch gaps are structural and unowned. If you want the VS Code ecosystem, copy VSCodroid: Code-OSS Web workbench + vscode-reh ARM64 server over localhost, add a native extra-keys bar and clipboard/keyboard bridges, and accept it's only good with a hardware keyboard, Android 13+, high-RAM devices. For a genuinely touch-first WebView product, use **CodeMirror 6 + @marimo-team/codemirror-languageserver** talking over WebSocket to on-device language servers; ship a native symbol row and disable-autocorrect attributes; track @codemirror/view point releases closely for GBoard regressions.
**(b) Native approach**: **sora-editor** is the only serious native core: use language-textmate (native oniguruma) for broad grammar coverage, language-treesitter where precision matters, and editor-lsp (lsp4j, socket) — budget engineering time to harden the experimental LSP client and pin 0.24.x prereleases. Mitigate single-maintainer risk by vendoring/forking; note LGPL-2.1 obligations. Native wins decisively on IME control, selection handles, magnifier, split-keyboard insets, and hardware-key handling; WebView/CM6 wins on LSP maturity, extension ecosystem, and cross-platform reuse.

## Confidence notes
Date conflict resolved by raw API: a WebFetch summary of the sora-editor releases page rendered 0.24.6 as "June 10, 2024", but direct curl of the GitHub API shows published_at 2026-06-10 (0.24.0–0.24.6 span Nov 2025–Jun 2026); trust the API. Sora-editor star count reported as "1.4k" by a page-summary fetch — likely a misread (historically ~3k); unverified, don't rely on it. Replit's CM6-for-mobile blog is from Sept 2021; Replit's 2025-2026 mobile app has been rebuilt agent-first (Agent/Preview swiping), so the editor's prominence there today is diminished — CM6 remains their web editor but I did not verify the current mobile app still exposes a full CM6 editing surface. "60% less highlighting time" (sora TextMate native oniguruma) is the project's own claim, not independently benchmarked. VSCodroid stats (42 stars) indicate a young project; its 4GB RAM figure is the project's recommendation, not a measured floor. 5k-line performance claims for all three engines are inferred from architecture (incremental parsing/virtualized rendering) and release notes rather than a head-to-head mobile benchmark — no public 2026 benchmark exists. Monaco issue statuses (#1504 open/Backlog, #4860 open, PR #4623 closed unmerged) were verified by direct fetch; per-comment maintainer statements beyond labels were not visible in fetched content. The claim that GBoard sometimes ignores web autocorrect/spellcheck attributes on contenteditable is well-attested in CodeMirror issue threads but was not separately confirmed by a dedicated source in this session.
