# runtime-exec

## Summary
On-device toolchain execution on stock Android in 2026 remains feasible but only via two proven paths: (1) the Termux model — targetSdk 28 APK exec'ing binaries from app-private storage, which still works on Android 16 (min installable targetSdk is only 24) but is Play-ineligible, or (2) the system_linker_exec trick ("/system/bin/linker64 /abs/path/bin"), which the official Termux Google Play build uses to run with a modern targetSdk. proot-distro adds glibc distros at roughly 40-50% benchmark penalty. The real 2026 threats are not exec() itself but: Google's developer-verification regime for sideloading (enforcement starts Sept 30, 2026 in 4 countries, global 2027, with an "advanced flow" and ADB escape hatches), the Android 12+ phantom-process killer (mitigable via a Developer-options toggle on Android 14+), Samsung One UI 8.x pinning backgrounded Termux to little cores even with unrestricted battery + foreground service (open bug), and the 16KB-page-size transition that Termux packages haven't completed. For a sideloaded enthusiast IDE on a Z Fold8, the workable architecture is a Termux-style bootstrap (aarch64 termux-packages binaries in app-private storage, exec'd via linker64), projects kept on private internal storage with direct file paths (never SAF for git), a specialUse foreground service + wakelock + battery exemption, and keeping the IDE UI in the foreground (split-screen) during heavy builds.

## Details
## 1. exec()/W^X status (Android 16/17, 2026)
Since Android 10, SELinux denies execve() of files in writable app storage for apps with targetSdk >= 29 ("Execution of files from the writable app home directory is a W^X violation") — [Termux-and-Android-10 wiki]. The exemption is keyed to targetSdk, not OS version: targetSdk-28 apps still exec freely on Android 16. No new enforcement landed in Android 15/16; the OS-level install block for old apps stops at targetSdk < 24 (Android 15/16), so targetSdk-28 APKs remain sideloadable/F-Droid-installable in 2026. Termux F-Droid builds (0.118/0.119.x) still run on One UI 8.x/Android 16; termux-packages fixed a targetSdk-related compat issue as recently as Jan 2026.

## 2. The Play-compliant workarounds
- **system_linker_exec**: `exec("/system/bin/linker64", "/abs/path/bin", ...)` — the ELF is loaded by the system linker, which is not subject to the app-data exec denial. The official **Termux Google Play build** (termux-play-store org, Fredrik Fornwall, v0.120, Android 11+) wraps every execve via LD_PRELOAD (termux-exec) to do this transparently. Known costs: /proc/self/exe lies (worked around with TERMUX_EXEC__PROC_SELF_EXE), some ptrace/debugger edge cases, and slight spawn overhead. Still functional on Android 16; Google has not closed it as of Aug 2026, but it is an unblessed hole that Google could close — the F-Droid targetSdk-28 build is the conservative fallback.
- **jniLibs/extractNativeLibs**: ship executables named `lib*.so` in the APK, set `extractNativeLibs=true`, exec from read-only `nativeLibraryDir` — explicitly allowed at any targetSdk. This is how Play-store IDEs (Pydroid 3, Cxxdroid) and nodejs-mobile-style embeddings stay compliant; limitation: binaries are fixed at APK build time (no user-installed native packages) unless combined with linker64 trick. `app_process` wrapping is only relevant for JVM/ART code, not native toolchains.
- **AndroidIDE** (androidide.com) demonstrates the ceiling of the Termux model: full Gradle + OpenJDK 17 + Android SDK running on-device, built directly on a Termux fork (targetSdk 28, F-Droid/sideload only).

## 3. proot-distro
proot fakes chroot/root via ptrace syscall rewriting — no root needed, works under Termux. Benchmarks: ~44% lower UNIXbench vs native/chroot ([termux-packages discussion #29944]); CPU-bound work only ~3-8% slower, but syscall/I-O-heavy work (git, compilers, npm/pip installs) is the worst case. Stable enough for daily use (Ubuntu/Debian/Alpine via proot-distro) but every phantom-process/CPU-throttle issue applies doubly. Use native termux-packages (aarch64 clang, git, node, python, rust are all packaged) and reserve proot for glibc-only tools (e.g., some language servers, JetBrains-family binaries).

## 4. Process killing (the real stability risk)
- **Phantom process killer** (Android 12+): max 32 child processes device-wide + "excessive CPU" kills → `signal 9` in terminals. Mitigations 2026: Android 14+ Developer-options toggle **"Disable child process restrictions"**; Android 12L/13: `adb shell settings put global settings_enable_monitor_phantom_procs false` (persists); Android 12: device_config (reverts on reboot). Samsung keeps the stock mechanism; an IDE must onboard users through this one-time ADB/dev-options step or aggressively limit its own process tree.
- **One UI 8.x CPU throttling** (termux-app #5086, open, Apr 2026): backgrounded Termux is scheduled only on little cores even with Unrestricted battery + foreground service, on S24+/S25U/S26U/Tab S9U — platform policy, no workaround except keeping the app visible (split-screen on a Fold is a genuine mitigation). Long builds while the screen is off will also hit Samsung "put to sleep" defaults (dontkillmyapp ranks Samsung worst).

## 5. Runtimes
- **Node**: Termux nodejs/nodejs-lts are current; code-server runs at usable speed on 3GB+ RAM flagships via localhost browser (extension marketplace partially restricted). nodejs-mobile (Node-as-.so, Play-compliant) had community releases through Apr 2026.
- **Python**: Chaquopy (CPython 3.8-3.13, in-process, pip wheels, MIT, free) for embedded scripting; Termux python for a real shell environment; python-for-android is Kivy-app-oriented, not toolchain-oriented.
- **WASM/WASI**: wasmtime/wasmer/wazero are mature runtimes (WASI p1) and embeddable (wazero especially, pure Go), but no official Android tier, no process model, no path to running gcc/git/node. Good for sandboxed plugin/extension execution only in 2026.

## 6. Storage
SAF pushes every op through ContentProvider IPC — cumulative latency across thousands of files; random I/O up to ~2x slower — git on SAF is impractical. Best practice: keep repos in app-private storage (`getFilesDir()`/`getExternalFilesDir()`) with direct POSIX paths (exactly what Termux does with $HOME), and expose a DocumentsProvider for other apps. MANAGE_EXTERNAL_STORAGE: banned on Play without approved use case, but a sideloaded app can use it for `/sdcard`-wide access.

## 7. Distribution & lifetime
Play in 2026: new apps must target API 36 — incompatible with the targetSdk-28 model; also 16KB-page compliance required (Termux packages not yet 16KB-ready — watch whether the Z Fold8 ships a 16KB kernel). Sideloading: developer verification enforcement starts Sept 30, 2026 (BR/ID/SG/TH; global 2027) — unverified installs survive via ADB or the deliberately painful "advanced flow"; a free 20-device account tier exists. F-Droid's future under verification is contested (open letter Feb 2026).
Foreground service: declare `specialUse` (dataSync/mediaProcessing get a 6h/24h cap from Android 15), hold a partial wakelock, request battery-optimization exemption, and instruct users to remove the app from Samsung sleep lists.

## Verdict
For a sideloaded enthusiast IDE in 2026: fork the Termux execution model — bootstrap of termux-packages aarch64 binaries in app-private storage, exec'd via system_linker_exec so you can use a modern targetSdk (or targetSdk 28 if staying F-Droid-only), direct-path private storage for projects, specialUse FGS + wakelock, one-time user setup (phantom-killer toggle, battery exemption), UI-visible builds on the Fold's split screen. This is proven (AndroidIDE, Termux itself, code-server users) and stable; everything else (pure WASI, SAF storage, Play distribution of a real toolchain) is not.

## Confidence notes
Cross-checked and solid: targetSdk-28 exec exemption + Android-14/15/16 install floor (Termux wiki + bayton.org matrix agree, targetSdk 28 > 24 floor); phantom-killer mitigation commands (termux-desktop doc + multiple guides agree); Play target-API 2026 dates (Google support page + several secondary sources); developer-verification dates and escape hatches (Google's own June 2026 blog + press). Conflicts/uncertainty: (1) proot overhead numbers vary hugely by workload — "44% lower UNIXbench" is one community benchmark, not authoritative; the 3-8% CPU figure came from a search-result synthesis I could not trace to a primary benchmark page, treat as indicative only. (2) Pydroid 3/Cxxdroid's exact exec mechanism (nativeLibraryDir exec vs in-process linking) was not verified from a primary source — the pattern is inferred from their Play presence and community descriptions; verify by unpacking the APK before relying on it. (3) Whether Google will close the system_linker_exec hole is unknown — no announced plans found, but the Play Termux build depends on it and Google approved that build, which is weak evidence of tolerance. (4) One UI 8.x little-core throttling is documented in one detailed open Termux issue (#5086) plus Samsung forum escalation; it may vary by device/firmware and has no confirmed Samsung acknowledgment. (5) Z Fold8 specifics (whether it ships a 16KB-page kernel, exact One UI 8.x behavior) could not be confirmed; 16KB risk to Termux packages is real but device-dependent — Termux tracking issues were still open at last verification. (6) Developer-verification 'advanced flow' friction details (reboot + 1-day wait) come from secondary reporting of a Google design, may change before global rollout. (7) Claim that code-server extension availability is limited under Termux is anecdotal from guides, not systematically tested.
