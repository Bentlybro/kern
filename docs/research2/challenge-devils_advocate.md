# devils_advocate

## Assessment
DEVIL'S ADVOCATE BRIEF — attacking "replace the code-server WebView with a native Android IDE UI"

## What I verified (URLs at end of each point)

**A1. The premise "it can't be fold-native" is FALSE, and this is the single biggest hole in the plan's justification.**
Fold-awareness (androidx.window `FoldingFeature`, tabletop/hinge, cover screen, real Android panes) is a property of the Activity and its layout tree. `WebView` is a plain `android.view.View`; it composes into a Compose `AndroidView` in one pane of a fold-aware scaffold exactly as `CodeEditor` (sora) would — the [native-editor] agent concedes this when it says "build the native chrome (panes, insets, key row, Termux terminal-view) first while the workbench keeps serving the editing surface." That sentence is the whole devil's-advocate case in one line, buried in a pro-native verdict. Tabletop mode, cover-screen layout, split panes, a native key row, native tabs, native file tree, native diff viewer and native terminal are ALL achievable with the code-server WebView still in the editor pane. Nothing in the fold requirement forces the editing surface to change. INFERRED (high confidence, standard Android): nothing about WebView blocks `FoldingFeature` observation.

**A2. Monaco's touch support is narrower-broken than the plan assumes, and the gap is attackable from the host app with PUBLIC, STABLE API.**
VERIFIED: `src/vs/editor/browser/controller/pointerHandler.ts` in microsoft/vscode ships `PointerEventHandler`, `TouchHandler`, and `PointerHandler`, wired to Gesture `tap` / `change` / `contextmenu`; pen input already dispatches with `inSelectionMode: true`. So Monaco is not touch-unaware — it has tap-to-position, touch scroll, and long-press context menu. What is missing is specifically: draggable selection handles, a magnifier, and Android soft-keyboard/IME fidelity.
VERIFIED: `ICodeEditor` publicly exposes `getTargetAtClientPoint(clientX, clientY)` ("gets the hit test target at coordinates clientX/clientY… returns a hit test target or null") and `getScrolledVisiblePosition(position)` ("gets the visible position for a position… relative to the top left corner of the editor"), plus `setSelection(...)` (4 overloads), `revealPositionInCenter(...)`, and `trigger(source, handlerId, payload)` — all in the shipped `monaco.d.ts` / documented API.
INFERRED (but the API surface is verified): that is precisely the set needed to draw **native** Android selection handles and a **native** magnifier as an overlay View on top of the WebView — px↔position both directions, plus a way to set selection and to fire editor commands. This is a bounded, ~2-4 week piece of work against a public API, not a rewrite. Compare: 6-9 months (their own [kotlin-lsp-dap] estimate) for the LSP half alone of the native path.
VERIFIED: microsoft/vscode #104336 (Android soft-keyboard backspace, opened 2020-08-09) is CLOSED with a concrete user-side workaround `"keyboard.dispatch": "keyCode"` — i.e. the flagship Android input bug has a settings-level fix.
URLs: https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/editor/browser/controller/pointerHandler.ts | https://microsoft.github.io/monaco-editor/docs.html | https://github.com/microsoft/vscode/issues/104336

**A3. The "every bespoke mobile editor got abandoned" premise is ALSO false — and when you check which ones survived, the data does not favour native.**
VERIFIED via GitHub API on 2026-08-06:
- Acode (Acode-Foundation/Acode) — 6.4k stars, MIT, ~3.6M downloads, shipping since 2019, actively maintained. Architecture: **JavaScript in a WebView with the Ace editor**, `www/` + webpack/rspack, no substantial Kotlin/Java editing core. This is the single most-used third-party Android code editor and it is a web editor in a WebView.
- CodeAssist (tyron12233) — `pushed_at` 2026-08-05, NOT archived, 1,637 stars, GPL-3.0, still alive.
- Squircle CE (massivemadness) — alive, activity through Jan 2026. Note it renamed from "Squircle **IDE**" to "Squircle **CE**" — scope retreat, not scope success.

**A6. The AI-agent workflow argument is the strongest one and the research panel almost entirely ignored it.**

A native rewrite of the *editing surface* is a 6-9 month investment in the smallest term. A native terminal (Termux `terminal-view`, already identified), a native diff viewer, and a native file tree — over the existing WebView — capture most of the value in a small fraction of the time.

## The shape of the attack
Strip out the two false premises (A1 fold-native requires native editor; A3 native = survival), apply the one verified cheap alternative (A2), weight by the actual workflow (A6), and the plan reduces to: **spend 6-9 months solo, take a bus-factor-1 dependency, lose folding and multi-cursor, to fix a problem that is 80% fixable in 3-4 weeks from the outside, in a workflow where that problem is no longer the bottleneck.** That is the honest strongest case against.

## Strongest objections
### [fatal] The stated justification is invalid: "it can't be fold-native" is false. Tabletop mode, cover-screen layout, hinge-aware panes, native tabs, native file tree, native terminal and native diff view are all properties of the host Activity/Compose layout. A WebView is a plain View and drops into a fold-aware scaffold pane exactly like sora's CodeEditor would. The [native-editor] verdict itself concedes this ("build the native chrome first while the workbench keeps serving the editing surface"). You do not need to replace the editing surface to get any of the fold features you named.
  Mitigation: Reframe the goal honestly: the only thing that actually requires replacing Monaco is in-editor touch text manipulation. Build the fold-native shell first, with the WebView in the editor pane, and only then decide whether the editing surface still hurts.

### [serious] The touch problem is far cheaper to fix than to replace. Monaco already has tap-to-position, touch scroll and long-press context menu (pointerHandler.ts: PointerEventHandler/TouchHandler/PointerHandler on Gesture tap/change/contextmenu). What's missing — draggable selection handles, magnifier, IME fidelity — is buildable as a NATIVE overlay View using PUBLIC, stable Monaco API: getTargetAtClientPoint (px->position), getScrolledVisiblePosition (position->px), setSelection, revealPositionInCenter, trigger. Weeks of work against a documented API versus 6-9 months (their own estimate) for the LSP half alone of the native path.
  Mitigation: None needed if you take the cheap path. If you insist on native, at least run the overlay experiment first as a 2-week spike — it is the cheapest possible test of whether the native rewrite is even necessary.

### [serious] The workflow argument inverts the whole priority stack. The developer's real loop is an agent CLI (verified: Claude Code on Termux/AVF is an established 2026 practice, with a dedicated claude-code-android project). In an agent-driven loop, free-form touch text entry is the SMALLEST term; terminal quality, diff review, and file navigation dominate. A 6-9 month native editing-surface project optimises the part of the workflow that AI agents just shrank, while the parts that grew (terminal, diff, review) are each a few weeks of native work over the existing WebView.
  Mitigation: Instrument two weeks of real usage: how many minutes are spent typing into the editor vs reading diffs vs in the terminal? Let that number, not aesthetics, authorise the rewrite.

### [serious] Opportunity cost against a working artifact. The app runs end-to-end today. The native path has a long trough with zero user-visible value: [kotlin-lsp-dap] says 6-9 months solo (4-5 if vendoring editor-lsp) for the LSP half alone, before any DAP, before folding (sora issue #85, open since 2021), before multi-cursor (sora #798, zero comments). The two live reference implementations of this exact stack are Klyx (ONE human, 854 commits, 14 months, still self-described alpha) and Code on the Go (12+ contributors above 20 commits, funded US nonprofit, ~18 months to R1). Neither resembles one person with a day job.
  Mitigation: Slice so every month ships something usable: native shell -> native terminal -> native diff -> native input assist -> (only then) native editing surface. Each slice must be independently valuable and independently abandonable.

### [serious] Solo-maintainer burnout is the actual documented killer, and the rewrite maximises exposure to it. AndroidIDE (3,039 stars) died with no technical reason given — the farewell says "You kept this project alive far longer than one developer ever could have alone." A long featureless trough with no users and no dopamine is exactly the condition that ends solo projects. Meanwhile the current WebView app keeps getting upstream VS Code improvements for free, forever, at zero maintenance cost to you.
  Mitigation: Never let the app be non-working for more than a week. Keep the WebView as the fallback editor pane permanently, behind a setting, even after sora lands.

### [manageable] sora-editor's bus factor is 73% one person: Rosemoe 1,981 commits vs the next human at 240. You would make a single hobbyist's roadmap your product's critical path, in a component you cannot easily swap late. Code on the Go had to patch into sora's package namespace (ContentLockAccessor, IDEEditorSearcher) to reach package-private APIs and vendored language-treesitter wholesale — budget the same, on top of maintaining that fork forever. LGPL-2.1-or-later is legally clean with GPLv3 (that part checks out) but licence compatibility was never the risk; the risk is roadmap capture.
  Mitigation: CodeEditor is a plain View, so the seam is genuinely swappable — keep the D9 CodeMirror 6 fallback alive as [native-editor] recommends, and treat sora as replaceable behind your own editor interface from day one.

### [serious] Language intelligence multiplies UI cost, not protocol cost. The panel is right that LSP4J transport is cheap, but the real bill is a dozen Compose surfaces per feature (completion popup with fuzzy filtering, signature help, hover cards, diagnostics gutter + list, quick fix menu, rename UI, references panel, symbol outline, semantic token theming) x correct UTF-16 incremental sync, on a 7-inch touch screen where none of the desktop interaction idioms transfer. Every one of these already exists, debugged, in the workbench you would be deleting. sora's editor-lsp is explicitly "Experimental, work in progress" and does NOT wire definition/references/rename/documentSymbol/foldingRange/codeLens/semanticTokens — that is precisely the UI-side work.
  Mitigation: Do not build DAP at all (there is no existing Android DAP client; you would be first, for a feature you will rarely use on a phone). Build LSP features strictly in usage order: diagnostics, then completion, then go-to-definition. Stop when the marginal one stops earning its keep.

### [manageable] Microsoft has permanently parked mobile touch — this is the one objection that survives in the PRO-native direction, and it is real. monaco-editor #1504 open since 2019-07-09, milestone Backlog, unassigned; the only community fix (PR #4623) closed unmerged with zero maintainer review and the thread bot-locked; #4946 ("keyboard not opening in Android", from someone building this exact Monaco-in-WebView Android IDE) open since 2025-07-27 with no response. Plus Chromium 40924170 on Android virtual-keyboard/innerHeight. You are betting on a component whose vendor has ignored your platform for seven years.
  Mitigation: The tax is permanent but bounded and compensable from OUTSIDE the WebView — the public hit-testing API (A2) means you own the fix and do not need Microsoft. The compensation code is also 100% reusable as the interaction design for a future native editor, so it is not wasted work under either plan.

## RECOMMENDATION
DO NOT do the rewrite now — but the answer is sequencing, not direction. My attack succeeded on the justification and the ordering; it did not succeed on proving native is wrong forever.

**Recommended plan, in order:**

1. **Kill the false premise first.** Build the native fold-aware Compose shell — hinge/tabletop layout via androidx.window FoldingFeature, cover-screen layout, real Android panes, native tab bar, native file tree, native command palette — with the code-server WebView still in the editor pane. This delivers 100% of the stated fold-native goal with 0% of the editor risk. Weeks, not months. Both [native-editor] and I independently reach this; it is the only recommendation with no dissent.

2. **Native terminal next, not native editor.** Termux terminal-view in its own fold pane. In an agent-CLI workflow this is the highest-traffic surface in the app and the WebView's xterm.js is the worst-served one on touch. Highest value per week of the whole project.

3. **Then M2: the native input overlay over Monaco.** Native selection handles + magnifier + native key row + IME proxy, driven from Kotlin via getTargetAtClientPoint / getScrolledVisiblePosition / setSelection / trigger. Ship "keyboard.dispatch": "keyCode" in the bundled settings while you're there. Budget 3-4 weeks. Two properties make this strictly dominant over rewriting now: it is ~10x cheaper than the native path, and every line of interaction design is reusable if you later swap in sora. It is not throwaway work under either future.

4. **Then measure, and let the number decide.** After steps 1-3, log two weeks of real use: minutes typing in the editor vs reading diffs vs in the terminal vs driving the agent. If in-editor typing is under ~15% of session time — which I expect, given the agent-CLI loop is verifiably the developer's workflow — the native editing surface has failed to earn 6-9 months and you stop here with a fold-native app that already works.

5. **Only if the pain survives step 4:** swap sora-editor in behind the shell seam you already built, LGPL relinking satisfied trivially by source availability. Keep the WebView as a permanent fallback behind a setting; keep the CodeMirror 6 fallback alive. Build LSP features strictly in usage order — diagnostics, completion, go-to-definition — and stop when marginal value dies. **Build no DAP at all**: there is no existing Android DAP client, you would be first, and step-debugging is the least plausible phone activity in the entire feature set.

**Explicitly reject** [remote-protocol]'s middle path (custom VS Code extension exposing your own WebSocket API) for now. Its headline benefit — "you keep the entire extension ecosystem" — is factually wrong for a code-server user who is already confined to Open VSX. It is the architecturally correct shape IF you ever go native (public semver-stable API, you own the protocol, extension host does the hard work), so keep it in the back pocket for step 5. Do not build it in advance of a decision it exists to serve.

**The honest bottom line:** the developer is proposing to spend the next six to nine months, alone, taking a 73%-one-person dependency and losing code folding and multi-cursor, in order to fix a problem that is roughly 80% fixable in a month from outside the WebView — in a workflow where AI agents have already demoted that problem from primary to incidental. The fold-native goal, which is the emotionally motivating one and the legitimate one, is achievable without any of that. Do the shell. Do the terminal. Do the overlay. Then look at the numbers and see if you still want the rewrite. If you do, you will start it from a strictly better position, with a working app the whole way, which is exactly the position AndroidIDE never had.
